# WL AI Director 平台 — 全量需求与整体审视

> 文档来源: 亮剑短剧项目中发现的平台级问题（亮剑仅作为测试用例）
> 审视角色: 专业开发 + 导演 双视角
> 审视维度: 需求完备性 / 前后矛盾 / AI 介入时机 / 流程合理性

---

> ⚠️ **重要说明**
>
> 本清单中的问题全部是 **WL AI Director 平台级别**的通用问题，
> 亮剑项目只是发现这些问题的测试用例。

### 阶段 A：AI 提示词工程（通用）

| 编号 | 来源 | 问题 | 类型 | 等级 | 平台级描述 |
|------|------|------|------|------|-----------|
| A01 | OP-001 | LLM 输出缺乏领域知识注入机制 | FEATURE | 🔴 | 用户无法向 AI 注入项目专属知识（历史/文化/风格等），AI 只能依赖训练数据中的通用印象。需提供"项目知识库"接口 |
| A02 | OP-002 | 中文输出丢失专业英文术语 | BUG | 🔴 | 提示词生成指定中文输出时，AI 自动翻译/丢弃了英文视觉风格术语（如 Rembrandt lighting、chiaroscuro），导致效果下降。应允许中英混写 |
| A03 | OP-003 | `generateCharacterVisualPrompt` 返回类型缺少 negative prompt | BUG | 🔴 | 同一套代码中有两个函数生成视觉提示词，其中一个返回了 negative prompt，另一个不返回。签名不统一 | ✅ 已修复 |
| A04 | OP-004 | 场景提示词硬编码风格 | BUG | 🟡 | `generateSceneVisualPrompt` 中 `getStylePrompt('anime')` 写死了 anime，未使用用户选择的 visualStyle |
| A05 | OP-005 | 质量标签去重只匹配英文 | BUG | 🟡 | `enhanceWithQualityTags` 用正则以英文关键词判断是否追加，中文等效词（"电影级画质"/"8K分辨率"）不触发，导致中英重复追加 |
| A06 | OP-007 | Negative prompt 未传递到 API 调用层 | BUG | 🟢 | negativePrompt 从生成函数返回到 imageAdapter 的链路中存在断裂，生成层传了但 callImageApi 没接 | ✅ 已修复 |
| A07 | OP-008 | 用户编辑的 visualPrompt 无"锁定"机制 | FEATURE | 🟢 | AI 每次重新生成都会覆盖用户手工编辑的提示词，缺少 manual/auto 切换标志 | ✅ 已修复 |


### 阶段 B：剧本→分镜映射（叙事逻辑）

| 编号 | 来源 | 问题 | 类型 | 等级 | 平台级描述 |
|------|------|------|------|------|-----------|
| B01 | OP-009 | 镜头与剧本场景映射错位 | BUG | 🔴 | 分镜生成未按剧本的场景划分做对齐，AI 按 storyParagraphs 数量生成 sceneId，段落数与场景数不一致时导致错位 |
| B02 | OP-010 | 分镜未提取剧本中的对白 | BUG | 🔴 | 分镜生成只用了场景概括文本，未从 rawScript 中定位并提取每句台词。需增加"对白提取"步骤 |
| B03 | OP-011 | 关键帧视觉提示词重复率过高 | BUG | 🔴 | 通用风格描述的机械拼接导致每个镜头的关键帧提示词几乎相同，AI 缺乏"每帧必须唯一"的约束 |
| B04 | OP-012 | 角色分配忽略"在场约束" | BUG | 🔴 | 分镜生成把全部角色分配给所有镜头，未检查"该角色在此刻是否物理在场"。需增加角色时间线约束 |
| B05 | OP-013 | 镜头数量按段落均分，未按情绪权重分配 | FEATURE | 🟡 | 情绪高潮段（开炮/牺牲）与平淡段落（集结）获得相同镜头数。应引入情绪权重算法 |
| B06 | OP-014 | 关键帧生成未使用已有角色/场景参考图 | BUG | 🟡 | 角色定妆照和场景图已生成，但关键帧生成时未作为 reference image 传入，同一角色在不同镜头中长相不一致 | ✅ 已修复（基础设施已就绪 + prompt 文字回退） |
| B07 | OP-015 | 运镜类型池太小 | FEATURE | 🟡 | 27个镜头中 Dolly/Tracking 占 16 次，Crane/Steadicam/POV/Handheld 等类型从未出现。需建立按情绪分类的运镜库 |
| B08 | OP-016 | Keyframe 类型只支持 start/end | FEATURE | 🟢 | 当动作跨时较长或变化复杂时，只有首尾帧无法控制中间过程。需支持 type: 'mid' 及 timing 字段 |
| B09 | OP-017 | AI 未提取剧本中的视觉细节 | FEATURE | 🟢 | 剧本中的手部动作、道具特写、微表情等"名场面"细节未被分配到对应镜头。需增加细节提取规则 |
| B10 | OP-006 | 角色服装/状态变更需手动创建变体 | FEATURE | 🟡 | 角色在不同场景的服装/状态变化（如日常装→战斗破损）需用户手动在资产库创建变体，未与剧本解析联动 |

## 第二部分：基于审视视角的矛盾分析

> 角色: 开发 + 导演 双视角

### 矛盾 1：「增加编辑自由度」 vs 「数据一致性」

**冲突表现**:
- C06（buildKeyframePrompt bug）让用户不敢编辑 visualPrompt — 编辑了也会被覆盖
- B06（缺少 reference image 传递）让用户就算编辑了角色描述，AI 也画不对
- C01（一些分镜字段只读）让用户改了部分参数但另一层级不同步

**开发者视角**：
- 修复优先级: C06 > B06 > C01
- C06 必须在前，否则用户编辑 = 白费

**导演视角**：
- 最痛的是 B01（场景映射错位）— 改完了编辑控件，但镜头本身所在场景就是错的
- 实际工作流应该是：先修 B01-B04（叙事骨架正确），再补 C01-C04（编辑能力），最后才是 D 系列（视频参数扩展）

**结论**: 之前的优先级（先做视频 Pipeline D 系列）与真实痛点（B 系列叙事错乱）存在矛盾。**开发资源的投入顺序应重新校准。**

### 矛盾 2：「Pipeline 工作流」 vs 「基本编辑功能不全」

**冲突表现**:
- Pipeline 设计（09）假设了完整的编辑能力，但 C01 显示 `cameraMovement` 至今不可编辑
- Pipeline 的 Camera 卡片依赖 `CameraChoreography` 编辑器，但这个编辑器只写入 `cameraChoreography` 字段，不同步 `cameraMovement`/`shotSize`
- Pipeline 的数据源本身不完整，上层展示再好看底层也是错的

**结论**: Pipeline 不是空中楼阁，其数据来自 shot 现有字段。必须先确保这些字段可编辑、数据一致，Pipeline 才有意义。建议：**先补最小编辑控件 + 数据同步，再建 Pipeline 统一入口。**

### 矛盾 3：「精细时间控制」 vs 「API 能力边界」

**冲突表现**:
- 用户期望精确控制视频中每个关键时间点的画面
- 当前 API（MSR/MKR）最高支持 3~5 个关键帧控制
- 即使接入全部 MKR 能力，也远达不到"逐秒控制"

**解决方案**: 放弃"逐秒控制"的思路，改为**"关键节奏点控制"**。Pipeline 引导用户标注转折点（如：枪响时刻、人物出场时刻），传给 MKR 作为关键帧位置，而非均匀分布。

### 矛盾 4：「AI 全自动」 vs 「手动精细调校」的平衡

**冲突表现**:
- 全自动模式下 AI 会覆盖用户编辑（C06）
- 全手动模式下又失去 AI 的效率
- 用户需要的不是二选一，而是**AI 生成 → 用户修改 → AI 按意图增量修改**的循环

**解决方案**: 引入 `visualPromptSource: 'auto' | 'manual'`（A07）机制。同时设计"增量修改"模式：用户圈定某部分文本或参数，AI 只改那一部分。

## 第三部分：更好的 AI 介入时机

当前 AI 介入时机：

```
剧本输入 → AI 拆分为分镜 → AI 生成关键帧 prompt → AI 生成图片 → AI 生成视频
```

全是**"生成时"**介入。缺少**生成后验证**和**用户修改时辅助**两个时机。

### 3.1 新增：生成后验证（AI Checkpoint）

在每个生成步骤完成后，自动增加一次 AI 校验：

| 步骤 | 校验内容 | 用途 |
|------|---------|------|
| 分镜生成后 | 每个镜头的场景归属是否正确？角色的在场时间线是否一致？ | 发现 B01/B04 类问题 |
| 关键帧生成后 | 连续帧之间角色/场景的一致性是否足够高？ | 发现 B06 类问题 |
| 视频生成后 | 视频内容是否与 prompt 描述基本匹配？ | 发现生成失败/跑偏 |

校验失败自动标记，而不是静默通过。用户可查看失败原因并选择"接受"或"回退重生成"。

### 3.2 新增：用户修改时辅助（Auto Suggest）

当用户修改某个字段时，AI 联动建议相关字段：

| 用户修改 | 联动建议 |
|---------|---------|
| 修改动作描述（actionSummary） | 建议更新的景别 + 运镜方案 |
| 修改对话（dialogue） | 建议语气/语速参数 |
| 调整运镜（cameraMovement） | 建议配套的 cameraChoreography 结构化数据 |
| 添加中间帧 | AI 根据前后帧自动生成视觉描述 |

### 3.3 新增：跨镜头一致性检查

当前每个镜头独立生成，不存在跨镜头的校验。AI 可检查：
- 连续镜头的角色位置连续性
- 时间线/光照的一致性
- 道具/场景的连续性

远期目标，第一版可暂缓。

## 第四部分：流程层面优化

### 4.1 当前流程的断裂点

```
剧本 → 分镜 → 关键帧 → 视频
  ①       ②       ③       ④
```

**断裂点 ①：剧本→分镜**
- 分镜生成不引用原始剧本 rawScript，只引用概括文本 storyParagraphs → B02 台词丢失
- 分镜不分场景边界 → B01 场景错位
- 分镜不校验角色在场 → B04 角色错配

**断裂点 ②：分镜→关键帧**
- 关键帧生成时不传递已生成的角色/场景参考图 → B06 角色不一致
- 关键帧数量硬编码为首尾帧 → B08 缺中间帧

**断裂点 ③：关键帧→视频**
- 只用了首尾帧（B08），中间过程不可控
- prompt 合成有副作用 bug（C06）

**断裂点 ④：全流程**
- 各阶段数据孤立 → 用户在剧本改了台词，导演工作台看不到更新
- 无回溯机制 → 改错了回不去
- 无版本管理 → AI 覆盖用户编辑后无法恢复

### 4.2 修复后的理想流程

```
                        ┌── 用户手动调整 ──┐
                        │                  ↓
剧本 → 分镜生成 → [分镜校验] → 分镜确认 → 关键帧生成
                        ↑                  │
                        │                  ↓
                     AI 校验           [关键帧校验]
                        │                  │
                        └──────────────────┘ (不通过则回退)
                                           │
                                           ↓
                                     关键帧确认 → 视频生成
                                                     │
                                                     ↓
                                                [视频校验]
                                                     │
                                                ┌────┴────┐
                                                ↓          ↓
                                             通过        不通过
                                                        (回退重新生成)
```

核心改进：
1. 每个阶段后增加 **AI 自动校验**（不需要用户主动触发）
2. 校验不通过 **标记问题但不自动回退**，由用户决定是否回退
3. 用户手动调整后 → **跳过自动校验**
4. 新增 **数据血缘追踪**

### 4.3 数据血缘

当前系统完全缺失，导致：
- 用户导出 JSON 后重新导入，不知道每个字段是怎么来的
- 多个 AI 模型切换时，不知道某个关键帧是哪个模型生成的
- 无法判断"用户编辑过" vs "AI 生成的默认值"

建议在每个生成字段上附加元信息：

```typescript
interface FieldMetadata {
  generatedBy: string       // 'ai:claude' | 'ai:gpt4' | 'user'
  inputSnapshot?: string    // 生成时输入摘要（如 actionSummary 的值）
  generatedAt: number
}
```

不存储在数据库层级（避免 schema 膨胀），而是存到 `shot.metadata` 或项目级别的 `generationLog` 中。导出 JSON 时作为可选项包含。

## 第五部分：系统性问题总结

### 5.1 最严重的 5 个问题（按伤害值排序）

| 排序 | 编号 | 问题 | 为什么最严重 |
|------|------|------|------------|
| 1 | B01/B02 | 场景映射错位 + 对白丢失 | 从根上否定了"剧本→分镜"流程的有效性。剧本输进去，分镜出来是另一个故事 |
| 2 | C06 | 合成 prompt 覆盖用户编辑 | 用户编辑被静默覆盖，彻底破坏信任——"我改了也白改" |
| 3 | A01/A02 | 提示词缺乏领域知识注入 + 术语丢失 | 所有后续生成（角色、场景、关键帧、视频）的基础质量都不对，任何项目都会遇到 |
| 4 | B06 | reference image 未传递到关键帧生成 | 角色/场景一致性无法保证，专业创作者不能接受 |
| 5 | C05 | 无 undo/redo | 让用户不敢尝试，创造力被抑制 |

### 5.2 开发与导演视角的分歧

| 维度 | 开发者自然倾向 | 导演真实需求 | 矛盾 |
|------|-------------|------------|------|
| 优先级 | D 系列（技术参数扩展） | B 系列（叙事逻辑正确） | 先修正叙事，再加能力 |
| 数据设计 | 追求类型安全、字段合理 | 追求"改了能看到效果" | 类型安全不能牺牲迭代速度 |
| AI 介入 | 一次生成，全自动 | 半自动，每个环节可介入修正 | 需要"AI draft + human refine"循环 |
| 交互 | 参数面板平铺 | Pipeline 工作流逐层深入 | 信息密度不同 |
| 持久化 | IndexedDB 结构化存储 | 导出 JSON 可读分享 | JSON 需要好读的 schema |

### 5.3 建议的路线（按依赖关系排列）

```
第一阶段：修叙事逻辑 + 还用户编辑权（改动的最小必要集）
  ├── B01：fix 场景映射（分镜生成 prompt 增加场景对齐约束）
```

## 第六部分：总结

> 站在开发 + 产品双视角给出的建议

**不要跳阶段**。Pipeline（第三阶段）很诱人，但第一阶段和第二阶段的 14 个问题是 Pipeline 能跑起来的基础。

原因很简单：
- Pipeline 的每个环节（Frame / Camera / Lighting / Performance / Output）都从 shot 的现有字段读取默认值
- 如果这些字段本身是错的（B01-B04）、不可编辑（C01）、或编辑了会被覆盖（C06），Pipeline 展示的只是错误数据的另一种排版

**当前所有 ~30 项优化点中，14 项属于平台本身的 bug，不是亮剑特有的配置问题。** 这些 bug 在任何剧本上都会出现。
